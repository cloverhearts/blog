リンクを開くだけでゲームが動けば、配布は簡単になります。インストーラー、OSの警告、環境設定を減らせるため、既存ゲームをブラウザで動かす方法としてWebAssemblyが最初に思い浮かびます。

しかし「WebAssemblyに変換すれば終わり」という説明は問題の一部しか示しません。ゲームはメインコードだけで動くものではありません。

## まずゲームの依存関係を並べる

ブラウザへ移せるかは、言語よりもゲームが期待する環境に左右されます。ファイル、グラフィックス、音声、ネットワーク、入力、外部ライブラリを確認します。

| 項目 | ブラウザでの質問 |
| --- | --- |
| グラフィックス | 既存の描画方式をウェブに合わせられるか |
| ファイル | ローカルパス前提の素材をどう読むか |
| 保存 | セーブデータをどこに置くか |
| 入力 | キーボード、マウス、ゲームパッドが同じように動くか |
| ネットワーク | ブラウザのセキュリティ規則を満たすか |
| 性能 | 初期ダウンロードとメモリ使用を許容できるか |

## 移植とエミュレーションは別の選択

ソースを修正できるなら、ウェブ向けに再ビルドする移植を検討できます。ソースがない場合や古い環境への依存が強い場合は、その環境をブラウザ内で再現するエミュレーションが必要かもしれません。

移植は性能と統合で有利ですが修正範囲が広く、エミュレーションは原作を保ちやすい一方で実行コストと互換性問題があります。

## 「動く」と「配布できる」の間

開発環境で最初の画面が出ても終わりではありません。ダウンロードが大きければ開始前に離脱されます。音声開始の条件、モバイルのメモリ、入力方式も異なります。

エンジン、フォント、音楽、映像の配布権も確認が必要です。技術的に実行できても、ウェブで再配布する権利が自動的に得られるわけではありません。

インストール不要の実行は可能性のある目標です。ただし答えはWebAssemblyという一語ではなく、ゲームが依存する環境を列挙し、ブラウザで代替できるか確認する過程にあります。
