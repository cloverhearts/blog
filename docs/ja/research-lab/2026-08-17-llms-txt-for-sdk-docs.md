SDK文書は人が読みやすいように作られます。長いサイドバー、タブ、折りたたみ例、複数ページへのリンクがあります。人は画面を探索して文脈を復元できますが、AIが必要な部分を安定して取得するには不便な場合があります。

この問題に対する公開提案の一つが`llms.txt`です。すべてのツールが従う公式標準ではありません。AIに主要文書と読む順序をテキスト中心で案内する小さな入口と考えると分かりやすくなります。

## 一つのファイルにすべてを入れる方式ではない

`llms.txt`を巨大な要約にすると管理が難しくなります。より現実的な役割は、概要、主要ガイド、API参照、例、注意事項の場所を示す文書の地図です。

AI向け入口では次の情報が重要です。

- 文書の目的
- 推奨する読順
- 機能ごとの原文位置
- バージョンと適用範囲
- 廃止された機能の表示

## 導入前後で何を比較するか

ファイルがあるだけではAIが読みやすくなったと判断できません。同じ連携課題を与え、結果を比較します。

| 項目 | 確認する質問 |
| --- | --- |
| 探索 | 必要な公式文書を見つけたか |
| 正確性 | 存在しない設定を作らなかったか |
| バージョン | 現行版の例を使ったか |
| 抜け | 必須の初期化やエラー処理を落としていないか |
| 根拠 | 参照した文書をもう一度見つけられるか |

比較なしに「AIフレンドリー」と呼ぶだけでは、人向け目次を別形式にコピーしただけになる可能性があります。

## 文書の品質が悪ければ入口だけが良くなる

`llms.txt`は不正確な本文を直しません。古い例と新しいAPIが混ざり、前提条件が分散していればAIも混乱します。

まず文書のバージョン、責任、例を整理し、その後でAI向けの地図を作る順序が安全です。AIが必ず`llms.txt`を読むとは限らないため、既存の検索、目次、各ページのメタデータも重要です。

重要なのはファイル名ではなく、エージェントが正しい原文を探し、根拠へ戻れる文書構造です。
