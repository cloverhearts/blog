SDK 문서는 사람에게 읽기 좋도록 만들어집니다. 왼쪽에는 긴 목차가 있고, 본문 사이에는 탭과 접히는 예제가 있으며, 관련 페이지는 여러 링크로 나뉩니다. 사람은 화면을 탐색하며 맥락을 복원할 수 있지만, AI가 필요한 부분만 안정적으로 가져오기에는 불편할 수 있습니다.

이 문제를 해결하려는 공개 제안 가운데 하나가 `llms.txt`입니다. 아직 모든 도구가 따르는 공식 표준이라고 보기는 어렵습니다. 사이트가 AI에게 주요 문서와 읽을 순서를 텍스트 중심으로 안내하는 작은 입구라고 이해하면 쉽습니다.

## 한 파일에 모든 문서를 넣는 방식은 아니다

`llms.txt`를 거대한 요약 파일로 생각하면 관리가 어려워집니다. 더 현실적인 역할은 문서 지도입니다. SDK의 개요, 핵심 가이드, API 참조, 예제, 주의 사항이 어디에 있는지 일관된 형식으로 알려 주는 것입니다.

사람용 홈페이지에서는 인기 기능과 시각적 탐색이 중요할 수 있습니다. AI용 입구에서는 다음 정보가 더 중요합니다.

- 문서의 목적
- 추천 읽기 순서
- 기능별 원문 위치
- 버전과 적용 범위
- 더 이상 쓰지 않는 기능에 대한 표시

## 전과 후를 무엇으로 비교할까

AI가 읽기 쉬워졌는지는 파일이 생겼다는 사실만으로 판단할 수 없습니다. 같은 연동 과제를 주고 다음 항목을 비교해야 합니다.

| 비교 항목 | 확인할 질문 |
| --- | --- |
| 탐색 | 필요한 공식 문서를 제대로 찾았는가 |
| 정확도 | 존재하지 않는 옵션을 만들어 내지 않았는가 |
| 버전 | 현재 버전에 맞는 예제를 사용했는가 |
| 누락 | 필수 초기화와 오류 처리를 빠뜨리지 않았는가 |
| 근거 | 답변이 참고한 문서를 다시 찾을 수 있는가 |

이런 비교 없이 “AI 친화적”이라는 표현만 붙이면 사람용 목차를 다른 형식으로 복사한 데 그칠 수 있습니다.

## 문서 품질이 나쁘면 입구만 좋아진다

`llms.txt`는 부정확한 본문을 고쳐 주지 않습니다. 오래된 예제와 새 API가 섞여 있거나 필수 조건이 여러 페이지에 흩어져 있다면 AI도 혼란을 겪습니다. 좋은 입구는 좋은 문서를 더 쉽게 찾게 할 뿐입니다.

따라서 먼저 문서의 버전, 책임, 예제를 정리하고 그다음 AI용 지도를 만드는 순서가 안전합니다. 또한 AI가 `llms.txt`를 반드시 읽는다고 가정해서도 안 됩니다. 기존 검색과 목차, 각 페이지의 메타데이터도 계속 중요합니다.

결론적으로 `llms.txt`는 SDK 문서를 AI가 읽기 쉽게 만드는 유용한 시작점이 될 수 있습니다. 다만 핵심은 파일 이름이 아니라 에이전트가 올바른 원문을 찾고 근거를 되짚을 수 있게 문서 구조를 정돈하는 데 있습니다.
