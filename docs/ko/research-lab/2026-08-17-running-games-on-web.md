링크를 누르자마자 게임이 실행된다면 배포는 훨씬 간단해집니다. 설치 파일을 내려받고, 운영체제의 경고를 통과하고, 실행 환경을 맞추는 과정이 줄어듭니다. 그래서 기존 바이너리 게임을 브라우저에서 바로 실행하는 방법을 생각하면 가장 먼저 WebAssembly가 떠오릅니다.

하지만 “코드를 WebAssembly로 바꾸면 끝난다”는 설명은 실제 문제의 절반도 담지 못합니다. 게임은 코드만으로 움직이지 않기 때문입니다.

## 먼저 게임의 의존성을 펼쳐 봐야 한다

브라우저로 옮길 수 있는지는 사용한 언어보다 게임이 기대하는 환경에 좌우됩니다. 파일 시스템, 그래픽 API, 오디오, 네트워크, 입력 장치, 외부 라이브러리를 어떻게 쓰는지 확인해야 합니다.

| 점검 항목 | 브라우저에서 생기는 질문 |
| --- | --- |
| 그래픽 | 기존 렌더링 방식을 웹 환경에 맞게 바꿀 수 있는가 |
| 파일 | 로컬 경로를 가정한 자원을 어떻게 불러올 것인가 |
| 저장 | 세이브 데이터를 어디에 보관할 것인가 |
| 입력 | 키보드, 마우스, 게임패드 동작이 같은가 |
| 네트워크 | 브라우저의 보안 정책을 만족하는가 |
| 성능 | 초기 다운로드와 메모리 사용을 감당할 수 있는가 |

## 포팅과 에뮬레이션은 다른 선택이다

소스 코드를 수정할 수 있다면 웹 환경에 맞게 다시 빌드하는 포팅을 검토할 수 있습니다. 반면 소스가 없거나 오래된 실행 환경에 강하게 의존한다면 해당 환경을 브라우저 안에서 흉내 내는 에뮬레이션이 필요할 수 있습니다.

포팅은 성능과 통합에서 유리할 수 있지만 수정 범위가 큽니다. 에뮬레이션은 원본을 더 많이 보존할 수 있지만 실행 비용과 호환성 문제가 생깁니다. 어느 쪽이 낫다는 답보다 원본 게임의 조건이 무엇인지가 먼저입니다.

## ‘실행됨’과 ‘배포 가능함’ 사이

개발 환경에서 첫 화면이 뜨는 것은 중요한 성과지만 끝은 아닙니다. 다운로드 크기가 너무 크면 사용자는 실행 전에 떠납니다. 브라우저마다 오디오 시작 조건이 다를 수 있고 모바일에서는 메모리와 입력 방식이 또 달라집니다.

게임에 포함된 엔진, 글꼴, 음악, 영상의 배포 권한도 확인해야 합니다. 기술적으로 실행할 수 있다는 사실이 웹으로 다시 배포할 권리를 자동으로 만들어 주지는 않습니다.

설치 없는 웹 실행은 가능성 있는 목표입니다. 다만 해답은 WebAssembly라는 단어 하나가 아니라 게임이 의존하는 세계를 목록으로 만들고 브라우저에서 각각 대체할 수 있는지 확인하는 과정에 있습니다.
