기존 SDK 문서는 대체로 사람을 독자로 삼습니다. 개발자가 목차를 읽고, 필요한 API를 찾고, 예제 코드를 조합해 하나의 기능을 완성합니다. 하지만 AI 에이전트가 코드를 작성하기 시작하면 SDK의 사용 방식도 달라집니다.

에이전트는 문서를 처음부터 끝까지 이해한 뒤 작업하지 않을 수 있습니다. 주어진 목표에 맞는 작은 기능을 찾고, 여러 조각을 조합하며, 실행 결과를 보고 다시 고칩니다. 이 환경에서는 기능이 많다는 사실보다 기능이 잘 나뉘고 조합된다는 사실이 중요해집니다.

## Composable하다는 말의 의미

Composable한 SDK는 각 기능이 독립적으로 이해되고, 예측 가능한 입력과 출력을 가지며, 다른 기능과 안전하게 결합될 수 있는 SDK입니다.

거대한 초기화 과정 하나에 수많은 설정이 숨어 있거나 호출 순서가 암묵적인 SDK는 사람에게도 어렵지만 에이전트에게는 더 어렵습니다. 한 단계가 실패했을 때 원인을 좁히기 힘들고 부분적으로 다시 시도하기도 어렵기 때문입니다.

## 에이전트가 조립하기 쉬운 구성 요소

다음 조건은 에이전트가 기능을 이해하고 조합하는 데 도움이 됩니다.

1. 하나의 구성 요소가 하나의 분명한 책임을 가진다.
2. 입력과 출력의 형태가 문서와 코드에서 일치한다.
3. 숨은 전역 상태와 암묵적인 실행 순서를 줄인다.
4. 실패 이유를 기계가 구분할 수 있는 형태로 돌려준다.
5. 작은 예제가 다른 예제와 자연스럽게 결합된다.

이 조건은 새로운 유행을 위한 것이 아닙니다. 테스트하기 쉬운 설계, 변경에 강한 설계라는 오래된 원칙과도 맞닿아 있습니다. AI 에이전트는 그 필요성을 더 크게 드러낼 뿐입니다.

## 문서도 구성 요소의 일부다

에이전트가 함수 이름만 보고 의도를 완벽히 추측할 것이라고 기대하면 안 됩니다. 어떤 상황에서 호출하는지, 무엇을 전제로 하는지, 실패하면 무엇을 확인해야 하는지가 가까운 곳에 있어야 합니다.

특히 예제는 완성된 대형 앱 하나보다 복사해 조합할 수 있는 작은 단위가 유용합니다. 인증, 데이터 조회, 변환, 저장처럼 책임이 나뉜 예제는 에이전트가 목표에 필요한 부분만 선택하기 쉽습니다.

## SDK는 API 묶음에서 재료 상자로 바뀐다

사람이 SDK를 사용하던 시대에는 좋은 안내서가 길을 설명했습니다. 에이전트 시대에는 길뿐 아니라 재료의 모양과 결합 규칙까지 명확해야 합니다.

Composable한 설계는 AI만을 위한 최적화가 아닙니다. 사람이 읽기 쉽고, 테스트하기 쉽고, 교체하기 쉬운 SDK가 에이전트에게도 좋은 SDK입니다. 결국 에이전트 친화성은 특별한 마법보다 모호함을 줄인 설계에서 시작합니다.
