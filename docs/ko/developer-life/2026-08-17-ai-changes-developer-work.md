AI가 코드를 쓰는 장면을 보고 있으면 개발자의 자리가 빠르게 줄어드는 것처럼 느껴집니다. 예전에는 한참 걸렸을 구현이 몇 문장 만에 만들어지기도 합니다. 그렇다면 개발자에게 남는 일은 무엇일까요?

AI와 함께 작은 개발 작업을 반복해 보면 코드를 직접 입력하는 시간보다 다른 일에 더 많은 힘을 쓰게 됩니다. 요구 조건을 구체화하고, 여러 선택지를 비교하고, 만들어질 결과를 미리 시뮬레이션하고, AI가 내놓은 결과가 실제 의도와 맞는지 판단하는 일입니다.

## 코딩이 줄어도 문제는 사라지지 않았다

AI는 구현 속도를 크게 높여 줍니다. 하지만 “무엇을 구현해야 하는가”가 흐린 상태에서는 빠른 속도로 엉뚱한 결과를 만들기도 합니다. 요구가 모호하면 AI는 빈칸을 그럴듯하게 채우고, 그럴듯함 때문에 잘못된 방향을 늦게 발견할 수 있습니다.

그래서 요청을 더 작은 질문으로 나누게 됩니다. 누가 쓰는지, 어떤 상황에서 실패하는지, 데이터가 없을 때는 어떻게 보일지, 기존 동작과 무엇이 달라지는지를 먼저 정합니다. 과거에도 필요했던 일이지만 AI가 빨라질수록 더 앞쪽으로 이동한 느낌입니다.

## 구현보다 판단의 밀도가 높아졌다

예전에는 하나의 구현을 완성하는 동안 자연스럽게 생각할 시간이 있었습니다. 지금은 여러 구현 후보가 빠르게 나옵니다. 그만큼 선택하고 버리는 판단이 짧은 시간 안에 몰립니다.

코드를 많이 만들 수 있다는 사실이 좋은 제품을 많이 만들 수 있다는 뜻은 아닙니다. 유지할 가치가 있는지, 다른 부분과 충돌하지 않는지, 사용자가 이해할 수 있는지를 판단해야 합니다. AI가 선택지를 늘려 줄수록 선택의 책임은 더 선명해집니다.

## 개발자의 산출물을 코드만으로 셀 수 없게 됐다

요구 조건 문서, 검증 기준, 실패 사례, 선택하지 않은 이유도 구현만큼 중요한 산출물이 됩니다. AI에게 다시 설명할 수 있는 형태로 남겨 두면 다음 작업의 품질도 높아집니다.

이 변화가 모든 개발자에게 똑같이 일어난다고 단정할 수는 없습니다. 분야와 제품, 책임 범위에 따라 직접 코딩의 비중은 크게 다릅니다. 다만 AI와 협업하는 환경에서는 코드를 만드는 능력만큼 문제를 정확히 표현하고 결과를 의심하는 능력의 비중이 커집니다.

AI가 개발자를 없앨지에 대한 거대한 예측보다 오늘 어떤 판단을 더 잘해야 하는지를 보는 편이 현실적입니다. 개발자의 일은 줄어드는 것이 아니라 구현 앞뒤로 넓어지고 있는 것 같습니다.
