# Multilingual Publishing and Discovery Contract

## Scope

This document defines language identity, independent localized publication,
static routes, translation grouping, explicit language selection, post-link
fallbacks, localized UI, and multilingual discovery for the blog.
`CONTENT_RULES.md` remains authoritative for authoring posts and managed pages;
`SEO.md` remains authoritative for discovery metadata.

## Supported and default languages

- Supported languages are English (`en`), Korean (`ko`), and Japanese (`ja`).
- Korean is the public default, unprefixed fallback, and normal source language
  used when the owner supplies a new post.
- English and Japanese system surfaces use complete secondary route trees under
  `/en/` and `/ja/`; individual post translations appear there as they are
  reviewed and published.
- Korean and English are the primary human UX, copy, and typography review
  languages. This priority does not remove or weaken Japanese publication,
  routing, translation, SEO, search, or accessibility requirements.
- The runtime-validated values in `config/site.yaml` are authoritative. Adding,
  removing, or changing a language is a schema, route, content-rule, SEO,
  search, design, and migration change—not a UI-only edit.

Every normal blog surface is localized: home, global navigation, footer, post
chrome, table of contents, categories, tags, archives, pagination, related
posts, search, empty/error states, consent controls, dates, RSS discovery, and
404 content. A page has one primary language; navigation and surrounding UI
must use the same language as its main content.

## Static route model

Korean uses unprefixed routes. English and Japanese use stable path prefixes:

| Logical page | Korean | English | Japanese |
| --- | --- | --- | --- |
| Home | `/` | `/en/` | `/ja/` |
| Post list page 2 | `/posts/page/2/` | `/en/posts/page/2/` | `/ja/posts/page/2/` |
| Post | `/posts/<slug>/` | `/en/posts/<slug>/` | `/ja/posts/<slug>/` |
| Category | `/categories/<id>/` | `/en/categories/<id>/` | `/ja/categories/<id>/` |
| Category page 2 | `/categories/<id>/page/2/` | `/en/categories/<id>/page/2/` | `/ja/categories/<id>/page/2/` |
| Tag | `/tags/<id>/` | `/en/tags/<id>/` | `/ja/tags/<id>/` |
| Archive | `/archive/` | `/en/archive/` | `/ja/archive/` |
| Search | `/search/` | `/en/search/` | `/ja/search/` |
| RSS | `/rss.xml` | `/en/rss.xml` | `/ja/rss.xml` |

Routes in `config/routes.yaml`, post links, and normal internal navigation are
locale-neutral logical routes. The shared resolver applies the active prefix
and then the deployment base path. Authors must not hard-code `/en`, `/ja`, a
GitHub Pages repository prefix, or a production origin into logical links.

Every localized route is a complete static HTML document. It contains its
title, navigation, body, taxonomy, related links, and language switcher in the
initial HTML and remains usable with JavaScript disabled. Client code never
translates or replaces the document body at runtime.

## Explicit language selection and user control

Every direct URL always remains on the requested static document. The site does
not inspect `Accept-Language`, `navigator.languages`, stored preferences, IP
location, or analytics state to redirect or replace a page. Browser language is
not a routing, recommendation, search, or analytics input.

Language changes happen only through visible, normal `<a>` links. The language
switcher identifies the current language and lists only existing published
variants of the same logical page. Site-wide system routes have all three
language links; a partially translated post exposes only its published
alternates. Missing translations are not synthesized, disabled links are not
rendered, and language selection never requires a query parameter or
JavaScript.

## Post translation groups

One logical post may have up to three source variants with the same relative
category, filename, slug, `translationKey`, and `originalLanguage`:

```text
docs/
├── en/programming/2026-09-13-cpp-programming.md
├── ko/programming/2026-09-13-cpp-programming.md
└── ja/programming/2026-09-13-cpp-programming.md
```

The source path determines language. The authored original must exist and be
published before any translation can be published. English and Japanese
translations may be added and published independently after review; a missing
or draft translation does not block another valid variant. Group fields that
affect identity or publication—`translationKey`, `originalLanguage`, `slug`,
relative filename, category, tags, `createdAt`, `updatedAt`,
`representativeImage`, and `related`—must match. Localized fields (`title`,
`description`, body prose, heading text, `translationStatus`, `draft`,
cover/social-image references and alt text, media alt text, captions, and link
descriptions) differ by language. The original variant is
`source`; an unreviewed AI translation is `ai-draft`; an owner-approved
translation is `reviewed`. Code, identifiers, URLs, citations, asset IDs, and
explicit heading anchors are preserved unless correctness requires a
documented change.

`originalLanguage` identifies the language in which the author created the
work. It is `ko` for the normal Korean-source workflow, but remains a per-post
field so future English- or Japanese-original work can be represented without a
global policy change. Exactly one published variant has a path language equal
to `originalLanguage`; every translated variant links back to that original.

The compiler uses locale-qualified IDs such as `ko:programming:cpp-programming`
and exposes only published route alternates in production artifacts. A
collection or related-post candidate represents the logical translation group
once. Its link resolves to the active page language when available, otherwise
to English, otherwise to Korean. If none of those variants is published, the
navigation item is omitted. A fallback entry uses the selected variant's real
title and description, declares that content language in markup, and visibly
labels the language; content is never synthesized into the surrounding locale.
Search and RSS remain strictly language-specific because they index or deliver
documents rather than resolve navigation links.

## Translation workflow

When the owner supplies a Korean post, an authoring agent must:

1. read `AGENTS.md`, `CONTENT_RULES.md`, and this document;
2. normalize the Korean source as the `ko` variant without changing its claims;
3. set `originalLanguage: "ko"` identically on all variants and create faithful
   English and Japanese variants in the same translation group; mark Korean
   `translationStatus: "source"` and the new translations
   `translationStatus: "ai-draft"`;
4. preserve code, durable links, citations, asset references, and explicit
   anchors; localize human prose, alternative text, captions, and headings;
5. publish the Korean source independently when its representative-image choice
   and normal production rules are satisfied; keep each unreviewed translation
   at `translationStatus: "ai-draft"` and `draft: true`;
6. request owner review of each translated variant and publish that variant
   independently only after changing it to `translationStatus: "reviewed"`;
   after a material source revision, return affected translations to draft
   until their fidelity is reviewed again;
7. run translation-group and content validation, or keep the affected variant
   as a draft and report uncertainty when a safe translation cannot be
   produced.

Agents must not add facts to make a translation read naturally. Ambiguous
technical terms may remain in their original form with a concise localized
explanation. Machine-created translations are never silently described as
reviewed. Production rejects `ai-draft`; publication authorization and factual
review remain the owner's decision.

## Post-language context metadata and optional UX

Post headers do not display translation banners, nuance warnings, or review
status. Every post artifact carries its current language, `originalLanguage`,
and published validated route alternates. These required,
presentation-neutral fields identify the authored original and power the
explicit language switcher.

A renderer may use that metadata for a concise language-context region after
the article body. When useful, it can identify and link the original language.
The region is an optional UX treatment rather than required post chrome or
publication metadata. Omitting it is not a release failure; the persistent
language navigation and static `hreflang` links remain the required controls.

No browser preference is resolved or written into post source or artifact
provenance. The optional context never redirects the reader. If rendered, its
original link is a normal canonical alternate, it exposes no
`translationStatus`, and it is excluded from article-body search indexing. The
original route is always resolved from validated alternates rather than a
handwritten URL.

Every localized post artifact also carries the same English metadata-only
owner declaration from `config/content-provenance.yaml`. It states that the
original work is human-authored and that AI assistance on that original work
was limited to proofreading. Because it applies to the original work, it never
replaces or weakens the current variant's internal `translationStatus` or any
optional visible language context. It is emitted only as custom document-head
metadata and is excluded from visible localized UI and search text.

## Shared assets and localized assets

Translation variants share post-owned assets under
`assets/content/<category>/<slug>/`; the build deduplicates identical bytes.
Each Markdown file supplies localized alt text and captions for the same asset.
An image or download containing language-specific visible text uses an explicit
suffix such as `architecture.en.png`, `architecture.ko.png`, or
`architecture.ja.png`, and each variant references the matching asset. Never
duplicate an identical binary merely to mirror the locale directory structure.

Open Graph metadata uses each variant's localized title, description, category,
tag labels, canonical URL, `ogLocale`, and image alternative text. A
text-bearing `socialImage` may differ by locale. When `representativeImage`
selects a generated card, it is rendered separately for each language so it
never places English text on a Korean or Japanese preview.

## UI messages, navigation, taxonomy, and formatting

- Framework-owned strings are typed by locale under `apps/blog-web/src/i18n/`.
- Intentional navigation entries provide `labels.en`, `labels.ko`, and
  `labels.ja`; internal blog links remain locale-neutral.
- Post-list, taxonomy, archive, pagination, and related-post link resolution
  uses the configured deterministic order: active language, English, Korean.
  A cross-language fallback link carries the target language and a visible
  localized language label. It never changes the current page locale.
- Category and tag IDs are stable lowercase ASCII values. Their visible labels
  come from `config/taxonomy.yaml` for all three languages. Post frontmatter
  stores IDs, not translated display labels.
- Dates, numbers, reading time, and accessibility text use locale-aware
  formatting with an explicit project timezone. They must not depend on the
  build machine locale.
- Each page emits the matching `<html lang>` value. Components never infer a
  language by inspecting prose.

## Search, RSS, sitemap, and 404

Search creates one deterministic index per language and loads only the active
language index. English, Korean, and Japanese tokenization/ranking fixtures are
required. Navigation, language-switcher text, and hidden fallback content are
excluded from indexed body text.

Each language has a post-only RSS feed. Korean uses `/rss.xml`, English uses
`/en/rss.xml`, and Japanese uses `/ja/rss.xml`. The root sitemap lists every eligible
localized canonical route. HTML `hreflang` links are the authoritative
alternate relationship; sitemap alternate annotations are intentionally not
duplicated. The root `404.html` is complete Korean fallback content; the build
also emits `/en/404/` and `/ja/404/`. Recovery links remain in the requested
404 page's language and no browser-language helper redirects between them.

## Managed pages

Managed pages remain independent, complete packages and are never automatically
machine-translated. To publish translations, create one package per language,
give each its own `page.yaml`, entry source, assets, and Open Design-compatible
`DESIGN.md`, and assign the same optional `translationKey`. Its explicit route
must follow the language route policy. Only existing published variants appear
in `hreflang` and the language switcher. An ungrouped managed page keeps its
declared language and exposes no nonexistent alternate.

## Validation requirements

A production build fails for mismatched shared group fields, missing,
unsupported, or inconsistent `originalLanguage`, invalid
`translationStatus`, an `ai-draft` published variant, absence of
the published declared original variant, duplicate translation keys within a locale,
missing UI/navigation/taxonomy labels, broken alternate/original links,
mixed-language page chrome, invalid `lang`/`hreflang`, automatic
browser-language navigation, cross-language search leakage, visible
translation review state, a fallback link that violates active-language,
English, then Korean priority, an unlabeled cross-language fallback, an
optional original link that does not resolve to a validated alternate, or a
canonical that points to another locale. Preview builds may render draft
variants, but never place them in production.
